# F9 · 传感器 → 场景重建：方法选型与工程清单（初学者问得最多的那些事）

> **定位**：`F0–F8` 讲的是「一条流水线怎么走」；`M0–M9` 讲的是「每个环节的原理与本项目实测」。
> 本篇回答另一类问题——**当你要真正动手做个东西时，到底选哪个方法？要多少数据？要什么卡？没见过的东西怎么办？**
> 风格：给你**能直接拿去选型**的四联表 —— 每个方法都标「**一句话定位 / 精度量级 / 算力·显存 / 需要的数据量**」，
> 并在能对上的地方钉上**本项目实测数字**（KITTI / TUM / 4Seasons / ModelNet40-C 等真实数据）。
>
> 一句话概括本篇：**几何讲"能不能算准"，选型讲"该不该用它、用得起吗"**。

## 0. 先给一张「全流程地图」：数据进来，场景出去

从传感器到场景，中间只有 **5 个工位**。你问的"单目/双目/检测/雷达用什么方法"，其实分别落在不同工位上：

```
   传感器                ① 位姿/几何          ② 稠密几何            ③ 语义                  ④ 场景表示          ⑤ 融合
┌──────────────┐   ┌────────────────┐   ┌──────────────┐   ┌────────────────┐   ┌──────────────┐   ┌────────────┐
│ 单目相机      │→ │ 单目 VO / SLAM  │→ │ 单目深度估计  │→ │ 2D/3D 检测      │→ │ 点云 / 网格    │→ │ 前/中/后融合 │
│ 双目相机      │→ │ 双目 VO(SGBM)  │→ │ 双目立体匹配  │→ │ 语义/实例分割   │→ │ 体素 / TSDF    │→ │ 标定 T_cl   │
│ RGB-D        │→ │ 深度+RANSAC ICP│→ │ 直接给稠密深度│→ │ 开放词汇 / 跟踪 │→ │ NeRF / 3DGS   │→ │ BEV 统一表示│
│ LiDAR        │→ │ ICP/GICP/NDT   │→ │ 稀疏点→累积   │→ │ 3D 检测         │→ │ 占据栅格 / BEV │→ │ 时空同步    │
│ IMU / 轮速    │→ │ 紧耦合 VIO/LIO │→ │ （给尺度/兜底）│→ │ —               │→ │ —             │→ │ —          │
└──────────────┘   └────────────────┘   └──────────────┘   └────────────────┘   └──────────────┘   └────────────┘
```

**读法**：横向是"从原始数据到可用场景"的推进，纵向是"你手里有什么传感器"。
比如你只有单目相机 → 只能走第 1 行；加了 LiDAR → 第 4 行走通，几何立刻变可信（这就是 `F5` 的动机）。

## 1. 单目视觉：一般用什么方法？

单目只有一台相机，**没有基线就没有绝对尺度** —— 这是所有单目方法的共同天花板，也是选型时的第一约束。

| 方法族 | 一句话定位 | 精度量级 | 算力 / 显存 | 需要的数据量 |
|---|---|---|---|---|
| **特征点 SfM / VO**（ORB-SLAM、自研 VO） | 一提一配一解，逐帧跟踪出轨迹 | ATE **0.1–1 m**（室内小场景）；尺度**不确定** | 轻，**CPU 可实时**；本项目自研 VO **9.8 fps @ CPU** | **零训练**（纯几何，无需数据） |
| **COLMAP（全局 SfM + BA）** | 离线把全部帧一起联合优化，最稳的经典解 | ATE **0.02–0.03 m**（TUM fr1/desk） | 重，**分钟级/几十帧**；显存 4–8 GB（可 CPU 慢跑） | **零训练** |
| **学习式前端 + 几何后端**（SuperPoint+LightGlue） | 换掉特征提取器，匹配更鲁棒 | ATE **0.28–0.37 m**（本项目 M5）；比 SIFT 稳但没质变 | 中，需 GPU；推理 **~10–30 ms/帧** | 特征匹配**预训练**（可用官方权重，无需自训） |
| **单目深度估计**（Depth Anything / MiDaS / Metric3D） | 一帧进、稠密深度出 | 相对深度很准；**绝对尺度需另定标**（相对误差 5–15%） | 中，GPU **~2–8 GB**，**20–80 ms/帧** | **百万级图像**预训练（自训要 ~10 万–1 M 图） |
| **前馈 3D 基础模型**（VGGT，本项目主用） | 一次前向同时出位姿 + 深度 + 点云 | 位姿 ATE **0.018 m**（合成）、**0.415 m**（真实夜间）；尺度 up-to-scale | 重，**≥16 GB 显存**跑 30 帧；本项目 RTX 4090 | **海量 3D 监督预训练**（不是你能自训的量级，**用开源权重**） |

> **📌 本项目实测锚点（M5 压力测试，13 种退化）**：
> | 条件 | 自研 VO | COLMAP | **VGGT** | LightGlue |
> |---|---|---|---|---|
> | 干净 | 0.529 | 0.026 | **0.018** | 0.305 |
> | 低光照-重 | 0.626(崩) | 0.312 | **0.019** | 0.282 |
> | 高斯噪声-重 | 0.626(崩) | 0.503 | **0.018** | 0.279 |
>
> **结论**：经典几何在**干净数据**上极准（COLMAP 0.026 m），但**退化即崩**；前馈模型几乎免疫。
> 选型口诀：**数据干净 + 要极致精度 → COLMAP；环境恶劣 + 要鲁棒 → 前馈模型（VGGT）**。

### 1.1 单目的三个"必踩坑"

1. **尺度漂移**：单目轨迹是"形状对、大小任意"。本项目 `P4` 就靠**真实 LiDAR 深度 median 比**把 VGGT 的 up-to-scale 轨迹定标到米制（**定标因子 ×72.433**，定标后轨迹 **125.16 m ≈ 7 m/s**，正是城市车速）——没有这步，地图大小就是错的。
2. **纯旋转退化**：相机原地转头（无平移）时，单目**无法三角化**任何点，深度完全不可解。这是几何硬限制，不是算法不行。
3. **快速运动 / 无纹理**：帧间重叠不足或墙面无特征 → 跟踪一断就丢（`M5` 中自研 VO 在重退化处卡在 **ATE 0.626** 的"塌缩定值"）。

## 2. 双目 / 多视图：一般用什么方法？

双目的核心优势：**一台已知基线的双目相机，天生就有绝对尺度**（不用像单目那样定标）。

| 方法族 | 一句话定位 | 精度量级 | 算力 / 显存 | 需要的数据量 |
|---|---|---|---|---|
| **块匹配 / SGBM**（OpenCV 传统立体） | 沿极线找同名点，算视差→深度 | 近距离好（<10 m，误差 %/米级）；纹理弱处空洞 | 轻，**CPU 实时**（1080p 约 10–50 ms） | **零训练** |
| **深度学习立体匹配**（RAFT-Stereo、CREStereo、IGEV） | 用代价体 + 网络回归视差，补上无纹理区 | 显著优于传统，KITTI 视差误差 **<1 px** | 中重，GPU **4–10 GB**，**50–200 ms/帧** | 大量**合成立体对**（SceneFlow ~3.5 万对）预训练 |
| **多视图立体 MVS**（COLMAP MVS、OpenMVS、MVSNet） | 多张图一起做稠密重建出点云/网格 | 重建精度 **毫米–厘米级**（可控场景） | 重，**分钟级**；显存 **8–24 GB** | MVSNet 类需 **DTU/BlendedMVS** 级数据预训练 |
| **双目 VO/SLAM**（ORB-SLAM2 双目、VINS-Fusion 双目） | 双目供尺度 + 几何前端做定位建图 | ATE **0.01–0.1 m**（室内） | 中，CPU 可实时 | **零训练** |

> **📌 本项目实测锚点（M10，真实数据）**：
> - **TUM RGB-D 反投影**：点云 **255,190** 点，投影回图像**重投影残差 0.0000 px** —— 证明投影几何（双目/深度的数学基础）自洽。
> - **KITTI 真实 LiDAR**：每帧 **~18,500** 个真实激光点，深度范围 **3.0–79.7 m**；稠密真值 **5.5–9.9 万点/帧**。
> - 相比之下，深度学习立体匹配需要的是"**大规模合成立体对预训练**"，这是**单人做不起**的部分 —— 所以实践中**用开源权重**。

### 2.1 双眼分辨口诀

| 想解决 | 单目 | 双目 |
|---|---|---|
| 尺度 | ❌ 需外部定标 | ✅ 天生有（基线×焦距） |
| 近距离稠密深度 | 靠学习式估计 | ✅ 传统方法就够 |
| 成本 / 体积 / 标定 | ✅ 便宜、免标定 | ❌ 贵、需精确标定与**在线校正** |
| 远距离 | ⚠️ 靠先验 | ❌ 视差趋于 0，**远处精度骤降**（深度误差 ∝ Z²） |

> **关键公式直觉**：双目深度 $Z = \dfrac{f \cdot B}{d}$（$f$ 焦距、$B$ 基线、$d$ 视差）。
> 视差 $d$ 在远处趋近 0 → **深度误差随距离平方增长**。这就是"双目只适合中近距离（一般 <20–50 m 视场景而定）"的根本原因。

## 3. 目标检测：一般用什么方法？精度如何？

检测回答的是「**有什么、在哪**」。分 2D 和 3D 两条线，精度指标也完全不同。

### 3.1 2D 检测 / 分割

| 方法族 | 一句话定位 | 精度量级 | 算力 / 显存 | 需要的数据量 |
|---|---|---|---|---|
| **两阶段**（Faster R-CNN） | 先出候选框再分类，准但慢 | COCO **mAP ~40–50** | GPU **~2–4 GB**，20–100 ms/帧 | COCO 级 **~12 万图** |
| **单阶段**（YOLO 系列） | 一遍网络直接回归框，快 | COCO **mAP ~40–55**（v8/v11） | 轻，**可端侧实时**（<16 GB 显存绰绰有余） | COCO 级 **~12 万图** |
| **DETR / Transformer** | 无锚框，集合预测，端到端 | COCO **mAP ~42–60** | 中重，GPU **4–8 GB** | COCO 级 + 长训练周期 |
| **语义分割**（U-Net / DeepLab / SegFormer） | 每个像素给类别 | mIoU **70–85**（Cityscapes 类） | 中，GPU **4–8 GB** | 像素级标注**很贵**：Cityscapes ~5,000 精细图 |
| **实例分割**（Mask R-CNN / SAM） | 每像素 + 每实例 | COCO mask mAP **~35–45** | 中重 | COCO 级 + 掩码标注 |
| **开放词汇**（OWL-ViT、Grounding DINO、SAM2） | 用**自然语言**找任意物体，不用重训 | 视提示而定，**召回不稳定** | 中重，GPU **4–12 GB**，50–200 ms/帧 | 图文对**海量预训练**（用开源权重） |

> **📌 本项目实测锚点（M7 / D1，真实数据）**：
> - OWL-ViT 开放词汇在真实水下数据上 **recall ≈ 0.001**（几乎全漏）；真实夜间影像 **≈ 7 命中/图**。
> - **诚实结论**：开放词汇能补"封闭集没见过"的洞，但**幻觉严重**（查 "a book" 返回 20 个框）——**它能当"发现未知"的探针，不能当"可信检测器"**。

### 3.2 3D 检测（自动驾驶主战场）

| 方法族 | 一句话定位 | 精度量级 | 算力 / 显存 | 需要的数据量 |
|---|---|---|---|---|
| **PointPillars** | 点云→柱体→2D CNN，快而实用 | KITTI 3D AP **~60–75**（车） | 中，GPU **4–8 GB**，**~20–40 ms/帧** | KITTI/nuScenes 级 **~1–10 万帧**（昂贵标注） |
| **SECOND / VoxelNet** | 稀疏 3D 卷积直接吃体素 | 略高于 Pillars | 重，GPU **8–16 GB** | 同上 |
| **CenterPoint** | 用"中心点"表示物体，无锚框 | nuScenes **NDS ~65–70** | 中重，GPU **8 GB** | nuScenes **~3 万帧** |
| **相机+激光融合**（BEVFusion、MV3D） | 在 BEV 空间统一融合 | nuScenes **NDS ~70+**，多模态加成明显 | 重，GPU **16–24 GB** | nuScenes/Waymo 级多模态数据 |
| **纯视觉 3D**（BEVDet、StreamPETR） | 只用相机反推 3D 框 | 低于融合，但成本低 | 中，GPU **8–16 GB** | nuScenes 级 |

> **类别数参考**（"要多少类"）：COCO **80 类**（通用）；Cityscapes 分割 **19 类**（驾驶）；nuScenes 检测 **23 类**（含各种车/人/障碍）；KITTI 检测 **3–8 类**。**类别越多，标注成本越高，且长尾越严重**。

## 4. LiDAR：一般用什么方法？

LiDAR 给的是**公制稀疏点云**，主战场是「**配准/定位**」与「**检测/分割**」。

### 4.1 点云配准（"两帧怎么对齐"，SLAM 的心脏）

| 方法族 | 一句话定位 | 精度量级 | 算力 / 显存 | 需要的数据量 |
|---|---|---|---|---|
| **ICP（点到点）** | 找最近点→解刚体变换→迭代 | 初值好时 **厘米级**；初值差易局部最优 | 轻，**CPU 实时**（可用 KD-tree 加速） | **零训练** |
| **点到面 ICP / GICP** | 用局部平面拟合，收敛更快更准 | **厘米级**，比点对点稳 | 轻中，CPU/GPU 均可 | **零训练** |
| **NDT（正态分布变换）** | 用体素内高斯分布代替点，抗稀疏 | **分米级**，适合 2D/3D 定位 | 中，**CPU 可实时**（Autoware 常用） | **零训练** |
| **学习式配准**（DCP、Predator） | 网络直接回归对应关系 | 优于 ICP 在**大初值误差/低重叠**场景 | 中，需 GPU | 大量人工配准对预训练 |
| **LiDAR SLAM**（LOAM / LIO-SAM / FAST-LIO） | 前端配准 + IMU 紧耦合 + 后端优化 | ATE **0.01–0.5 m**（KITTI 里程计类） | 中，**CPU/GPU 混合可实时** | **零训练** |

> **📌 本项目实测锚点（P4）**：真实驾驶中，本项目用**同一套 VGGT 位姿**把 30 帧真实 LiDAR 反投影到世界系累积，共 **564,951** 个真实激光点，建成 ≈**150×190 m** @ 0.4 m 栅格的 BEV 地图。**这正体现了"视觉管方向、激光管几何"的分工**。

### 4.2 点云检测与分割

| 方法族 | 一句话定位 | 精度量级 | 算力 / 显存 | 需要的数据量 |
|---|---|---|---|---|
| **地面分割**（RANSAC 平面 / Patchwork++） | 把地面点剔掉，只留障碍物 | 规则场景很稳 | 极轻，**CPU 实时** | **零训练** |
| **聚类分割**（DBSCAN / 欧氏聚类） | 把邻近点聚成物体 | 依赖参数，无类别 | 轻，CPU 可实时 | **零训练** |
| **3D 语义分割**（PointNet++ / MinkowskiNet / Cylinder3D） | 给每个点打语义标签 | nuScenes/Cityscapes mIoU **60–80** | 中重，GPU **8–16 GB** | **~1 万帧级**精细标注 |
| **3D 检测** | 见 §3.2 | 同上 | 同上 | 同上 |

## 5. 场景表示：重建出来的东西"装在哪"？

这一步决定"下游能不能用"。同一个场景，装法不同，下游能做的事完全不同。

| 表示 | 一句话定位 | 精度 / 保真度 | 算力 / 显存 | 需要的数据量 |
|---|---|---|---|---|
| **点云** | 原始点集合，最简单 | 几何准、无表面、无拓扑 | 低（存储随点数线性增长） | 直接来自传感器/重建 |
| **网格 Mesh** | 三角面片，有表面 | 表面平滑、可渲染/仿真 | 中 | 来自 MVS / TSDF |
| **体素 Voxel** | 把空间切成小方块 | 分辨率决定精度，存储**立方增长** | 重（高分辨率显存爆炸） | 来自点云栅格化 |
| **TSDF** | 每个体素存"到表面的带符号距离"，多帧**融合** | 融合平滑、抗噪；**本项目 M2 用它重建出 84 万顶点网格** | 中重，GPU 有 CUDA 加速实现 | 多帧深度图（数十帧级） |
| **占据栅格 Occupancy** | 每格"有东西/没东西"，规划最爱 | 粗但**对规划友好**（本项目 P1/P2 用 0.1 m 栅格做 A*） | 极轻，**CPU 实时** | 来自深度/LiDAR |
| **BEV** | 俯视 2D 张量，检测/融合最爱 | 丢失高度细节，但**统一多传感器** | 中，GPU **4–8 GB** | 多传感器数据 |
| **NeRF** | 用 MLP 隐式表示，渲染极美 | 渲染照片级，**几何精度一般**，训练慢 | 重，GPU **12–24 GB**，**训练小时级** | 数十–数百张多视角图 |
| **3D Gaussian Splatting (3DGS)** | 用一堆 3D 高斯球显式表示 | 渲染快且真实，**可实时** | 训练重（**12–24 GB**），渲染轻 | 数十–数百张多视角图 |

> **选型口诀**：要**规划避障** → 占据栅格；要**多传感器检测** → BEV；要**仿真/渲染** → 网格 / 3DGS；要**物理可观测量** → 点云 / TSDF。

## 6. 融合：不同数据"怎么处理到一起"？

融合的三要素：**标定（空间对齐）+ 同步（时间对齐）+ 架构（在哪一层合）**。

### 6.1 空间对齐（标定）

| 标定类型 | 做法 | 精度 | 需要什么 |
|---|---|---|---|
| **相机内参** | 棋盘格张正友标定 | **亚像素** | 标定板 + 20 张图 |
| **相机–LiDAR 外参** | 靶标法（棋盘格+反光孔/ArUco） | **厘米级** | 特制靶标，下线标定常用 |
| **相机–LiDAR 无靶标** | 利用图像边缘 ↔ 点云深度不连续一致 | **略低**，依赖场景 | 无需靶标但易受场景影响 |
| **多相机 / IMU** | 联合标定（可含时间偏移 $t_d$） | 需精细优化 | 专用标定流程 |

> **📌 本项目实测**：投影公式在 TUM 上**重投影残差 0.0000 px**（K 自洽）；KITTI 真实 LiDAR 深度范围 **3.0–79.7 m**，投影到 image_02 完全吻合。

### 6.2 时间对齐（初学者极易忽略，但最致命）

| 问题 | 现象 | 解决办法 |
|---|---|---|
| **时间戳不同源** | 相机 30 Hz、LiDAR 10 Hz、IMU 200 Hz，点对不上 | **硬件触发（PTP/gPTP）** 或软件插值对齐 |
| **曝光/滚动快门** | 高速运动时图像扭曲，与点云错位 | 全局快门相机 / 滚动快门补偿 |
| **运动畸变** | 一帧 LiDAR 扫描期间车在动 → 点云被"拉斜" | **去畸变（motion compensation）** 用 IMU/里程计校正 |

### 6.3 融合架构

| 架构 | 在哪合 | 优点 | 缺点 | 落地建议 |
|---|---|---|---|---|
| **前融合** | 原始数据层（点云+图像→统一体素/BEV） | 信息损失最小 | 需严格同步/标定，难训练 | 学术前沿 |
| **中融合** | 特征层（交叉注意力） | 精度与鲁棒平衡 | 需精心设计融合层 | 主流学界方向 |
| **后融合** | 决策层（各出结果再关联） | **解耦、容错好** | 信息利用不充分 | **量产首选**（某传感器坏了仍能跑） |

## 7. 训练：实际要多少数据？多少类？没见过的东西怎么办？

这一节是**初学者最想问、也最容易低估**的部分。

### 7.1 数据量参考（量级）

| 任务 | 最小可跑 | 能上台面 | 工业级 |
|---|---|---|---|
| 2D 检测 / 分割 | 几百–几千图（微调） | 1 万–12 万图 | 百万级 |
| 3D 检测 | 几千帧（微调） | 1 万–3 万帧 | 10 万+ 帧 |
| 深度估计 | 1 万图 | 10 万–100 万图 | 百万+（含合成） |
| 立体匹配 | 1 万立体对 | 3.5 万对（SceneFlow） | 10 万+ |
| 3D 基础模型（VGGT 类） | —（**做不了**） | — | **百万级 3D 监督，多机多卡数周** |

> **核心现实**：**除了"微调"，绝大多数人不会从头训练**。
> 正确姿势是 **用开源预训练权重 → 在自己的小数据上微调（fine-tune）或零样本直接用**。
> 本项目全部如此：VGGT / OWL-ViT / YOLO 均用开源权重，**没有一项是从零训的**——这不是偷懒，这就是工业界的真实做法。

### 7.2 多少类？长尾怎么办？

- **类别体系**：COCO 80 / Cityscapes 19 / nuScenes 23 / KITTI 3–8。类越多，标注越贵，**长尾（rare class）越严重**。
- **长尾现实**：真实世界里 80% 的样本属于 20% 的常见类；罕见类（救护车、施工路障）样本极少 → **模型在关键场景失效**。
- 应对手段：

| 手段 | 做法 | 代价 |
|---|---|---|
| **重采样 / 重加权** | 给稀有类更高采样权重 | 易过拟合稀有类 |
| **数据增强 / 合成** | 复制粘贴、仿真生成（本项目 `P2` Gazebo 退化图库） | 有 sim-to-real gap |
| **开放词汇模型** | 用文本提示找新类，不重训 | 精度不稳、有幻觉（M7 实测 recall≈0.001） |
| **检测 + 分割组合** | 封闭集检测兜底 + 开放词汇发现 | 系统复杂度上升 |

### 7.3 没见过的物体怎么办？（OOD：Out-of-Distribution）

这是**初学者最容易漏、工业界最头疼**的问题。按代价从低到高：

1. **几何兜底（最实用）**：不认识的物体，**形状还在**——点云/深度会告诉你"这里有个东西"，占据栅格照样把它标成障碍 → **能避障**（本项目 `P1/P2/P3` 就是这套：规划只关心"格子被占"，不关心"是什么"）。
2. **开放词汇检测**：用语言查询去"发现"未见类（`M7`），但**只能当探针**。
3. **异常检测（OOD detection）**：让模型输出"我不知道"，而不是自信地错。
4. **在线学习 / 数据回传**：把罕见样本回传重训（工业级闭环，需要车队规模）。
5. **冗余传感器**：一路失效另一路兜底（这就是 `F5` 融合的**安全意义**，不只是精度意义）。

> **一句话**：**感知系统不该假设"见过所有东西"；工程上要保证"没见过也能安全停/绕"**——这就是 `F6` 兜底逻辑存在的理由。

## 8. 算力：要什么设备来跑？

| 场景 | 典型芯片 | 算力（TOPS） | 显存 | 能跑什么 |
|---|---|---|---|---|
| **云端训练** | A100 / H100 / 4090 | 数百–上千 | **40–80 GB** | 从头训练大模型（VGGT、检测大模型） |
| **桌面开发 / 研究** | RTX 4090 / A6000 | ~100–300 | **24–48 GB** | 本项目全部实验（VGGT 30 帧 ≈16 GB） |
| **车载 / 机器人（高配）** | Orin AGX / 双 Orin | ~250 | **32–64 GB 统一内存** | BEV 融合 + 多路相机 + LiDAR 实时 |
| **车载 / 机器人（主流）** | Orin NX / Xavier | **70–100** | 8–16 GB | 纯视觉 BEV / 轻量检测，多任务分时 |
| **端侧 / 低功耗** | RK3588 / Jetson Nano / 地平线 | **1–6** | 2–8 GB（共享内存） | INT8 量化后的轻量检测/深度（本项目 `M8`） |
| **纯 CPU** | x86/ARM 多核 | — | — | 几何类方法（VO **9.8 fps @ CPU**）可跑 |

> **📌 本项目实测锚点（M8 端侧）**：用"算力预算"模拟端侧（本机无需真机）+ **INT8 PTQ 真跑一遍**。
> 结论：**端侧不是"能不能跑"，是"实时 + 省电 + 精度可接受"的三角权衡**；**INT8 PTQ 是性价比最高的第一招**。

**经验法则**：
- **几何方法（VO/ICP/NDT）**：CPU 就能实时，是**资源受限场景的保命选项**。
- **深度模型**：吃 GPU 显存，**显存是硬门槛**（VGGT 要 ≥16 GB 才舒服）。
- **端侧**：先量化（INT8），再剪枝，最后考虑换更小的模型 —— 顺序别搞反。

## 9. 初学者想不到、但实际一定会遇到的清单

你问"实际中还会有哪些要考虑"——下面这些**教科书不写、一上真机就撞上**：

### 9.1 传感器层面

| 项目 | 为什么重要 | 踩坑后果 |
|---|---|---|
| **时间同步** | 多传感器频率不同、时钟不同源 | 点云与图像错位 → 融合全废（§6.2） |
| **标定漂移** | 震动/温度变化让外参慢慢变 | 融合精度逐月下降，需**在线标定/定期重标** |
| **运动畸变** | 一帧 LiDAR 扫描期间车在动 | 点云"拉斜"，直墙变斜墙 |
| **坐标系链（TF 树）** | 相机→车体→雷达→世界 层层变换 | 一个环节搞错，全局结果错（**最难 debug 的 bug**） |
| **传感器失效检测** | 镜头脏污/雨雪/遮挡 | 系统必须**知道自己瞎了**，否则自信地撞 |

### 9.2 数据与标注层面

| 项目 | 为什么重要 |
|---|---|
| **标注一致性** | 多人标注标准不一 → 模型学不出稳定边界 |
| **标注成本** | 3D 框标注比 2D 贵 **5–10 倍**；像素级更贵 |
| **数据偏差** | 只在晴天采 → 雨天必崩（本项目 `M5` 用退化图谱专门量化这事） |
| **隐私合规** | 街景含人脸/车牌，需脱敏（GDPR/个保法） |
| **数据版本管理** | 数据集改了要能复现旧结果，否则实验不可信 |

### 9.3 算法与工程层面

| 项目 | 为什么重要 |
|---|---|
| **动态物体污染建图** | 车/人按"静态"拼进地图 → 地图有幽灵（本项目 `P4` 专门做**移动目标检测**把动的标红排除） |
| **回环检测** | 没有回环，SLAM 漂移无法修正（走一圈回原点会对不上） |
| **地图一致性** | 重访同一地点必须对齐，否则导航不可用 |
| **计算资源调度** | 多任务抢 GPU，需要**分时/降频/分级**策略 |
| **失败模式与兜底** | 感知不确定时必须**降级运行**（减速/刹停/切传感器），见 `F6` |
| **评测协议** | 用什么指标（ATE/mAP/mIoU）、怎么对齐、报不报失败率 —— **不诚实评测 = 自欺**（本项目 `M5` 明确写"合成≠真实"） |
| **实时性预算** | 端到端延迟（传感器曝光→控制指令）必须满足控制周期，通常 **<100 ms** |

### 9.4 安全与合规（最容易被忽视）

- **功能安全**：ISO 26262（汽车）/ IEC 61508。感知是"安全相关"的，要有失效冗余。
- **可解释性**：出事故要能复盘"当时系统看到了什么、为什么这么决策"→ 必须**记录原始数据 + 中间结果**。
- **最坏情况优先**：不要只测"最好结果"，要测**最坏 1%**（长尾）。

## 10. 一页速查：传感器 → 方法 → 数据 → 算力

| 你手里有 | 位姿方法 | 稠密几何 | 检测/语义 | 需要的数据量 | 典型算力 |
|---|---|---|---|---|---|
| **仅单目** | 单目 VO / VGGT | 单目深度估计 | 2D 检测 / 开放词汇 | 零训练（几何）/ 预训练（深度、检测） | CPU 可行 / GPU 4–8 GB |
| **双目** | 双目 VO / VINS | SGBM / 学习式立体 | 2D 检测 | 零训练 / SceneFlow 级预训练 | CPU 实时 / GPU 4–10 GB |
| **RGB-D** | 深度 + ICP | 直接稠密 | 2D/实例分割 | 同上 | CPU/GPU 均可 |
| **LiDAR** | ICP/GICP/NDT / LIO | 稀疏点累积 | 3D 检测 / 点云分割 | 零训练 / 1–3 万帧标注 | CPU 实时 / GPU 8–16 GB |
| **相机+LiDAR** | 后融合位姿 | BEV 统一 | BEVFusion 多模态 | nuScenes 级多模态 | GPU 16–24 GB |
| **+IMU/轮速** | 紧耦合 VIO/LIO（最稳） | 去畸变 + 尺度 | — | 零训练 | CPU/GPU 混合实时 |

## 11. 三条核心结论

1. **"哪个方法好"没有绝对答案，只有"在什么约束下选谁"**：数据干净要精度选经典几何（COLMAP ATE 0.026 m），环境恶劣要鲁棒选前馈模型（VGGT 0.415 m 黑夜仍活）；**先问约束，再选方法**。
2. **尺度、时间、标定是三个"看不见的地基"**：单目无尺度（本项目靠 LiDAR median 定标 ×72.433）、多传感器不同步、外参漂移——这三件事任何一个出错，上层算法再强也白搭。
3. **工程上真正决定成败的是"没见过怎么办 + 算力够不够 + 出错怎么兜底"**，不是"模型涨了几个点"：**几何兜底 + 开放词汇探针 + INT8 量化 + 降级策略**，才是能上线的组合。
